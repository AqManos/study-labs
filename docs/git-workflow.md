# Работа с Git: шпаргалка

## 1. Что где находится

| | Git | GitHub / GitLab / Bitbucket / GitVerse |
|---|---|---|
| Что это | программа контроля версий | веб-сервис с удалёнными репозиториями |
| Где работает | локально, на вашем компьютере | в облаке |
| Нужен интернет | нет | да |
| Зачем | история изменений, ветки, откаты | резервная копия, совместная работа, PR |

Локально — просто Git. Удалённо — GitHub и аналоги. Это разные вещи.

## 2. Первичная настройка

```bash
git --version

git config --global user.name "Имя Фамилия"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main

# проверить
git config --global --list
```

## 3. Создание и клонирование

```bash
# новый локальный репозиторий в текущей папке
git init

# скопировать удалённый репозиторий на компьютер
git clone <URL>
```

## 4. Ежедневный цикл

```bash
git pull                  # забрать изменения коллег ДО начала работы
git switch -c lab-01      # новая ветка под задачу
# ... работа ...
git status                # что изменено
git add <файл>            # подготовить файл к коммиту
git diff --staged         # проверить, что именно попадёт в коммит
git commit -m "docs(lab-01): добавлен отчёт"
git push -u origin lab-01 # отправить ветку на GitHub
```

Дальше — Pull Request в веб-интерфейсе GitHub.

## 5. Ветки

```bash
git branch                    # список веток
git switch -c feature/login   # создать и переключиться
git switch main               # переключиться на main
git merge feature/login       # влить ветку в текущую
git merge --abort             # отменить проблемный merge
git branch -d feature/login   # удалить слитую ветку
```

`git checkout` — старая команда, `git switch` — современная и безопаснее
(не даёт случайно переключиться на коммит вместо ветки). В лекции используется
`checkout`, работать можно и так.

Именование веток:

- `lab-01`, `lab-02` — лабораторные;
- `hw-01`, `hw-02` — домашние задания;
- `fix/typo-in-readme` — мелкие исправления;
- `feature/<название>` — новый функционал.

## 6. Коммиты

```bash
git commit -m "feat(lab-01): реализован парсер"
git commit --amend            # поправить последний коммит (только локально!)
git log --oneline --graph     # история
git show <commit>             # что было в коммите
git blame <файл>              # кто и когда менял строки
git reflog                    # журнал перемещений HEAD — спасает от потери коммитов
```

Хорошее сообщение коммита отвечает на вопрос «что и зачем изменилось»:

```text
feat(lab-01): добавлен расчёт выборки
fix(lab-01): исправлено деление на ноль
docs(lab-02): добавлены исходники диаграмм
chore: обновлён .gitignore
```

Типы: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`.

## 7. Pull Request (PR)

PR — это **не команда Git** и не `git pull`. Это заявка в веб-интерфейсе
GitHub на вливание вашей ветки в целевую (обычно `main`).

Порядок:

1. Создать ветку от актуального `main`.
2. Сделать коммиты и `git push -u origin <ветка>`.
3. На GitHub нажать **Compare & pull request**.
4. Заполнить описание: что сделано и как проверить.
5. Дождаться ревью/CI, при необходимости — доработать.
6. Нажать **Merge pull request**.

В GitLab PR называется **Merge Request (MR)**.

## 8. Конфликты

Конфликт возникает, когда два человека изменили одну и ту же строку.

```bash
git pull
# Git сообщает: CONFLICT (content): Merge conflict in <файл>
```

В файле появляются маркеры:

```text
<<<<<<< HEAD
ваша версия
=======
версия из удалённого репозитория
>>>>>>> origin/main
```

Нужно вручную оставить правильный вариант, удалить маркеры, затем:

```bash
git add <файл>
git commit
```

Если конфликт не нужен и хочется начать заново:

```bash
git merge --abort
```

## 9. .gitignore

Файл в корне репозитория. Внутри — шаблоны того, что Git должен игнорировать:
`.venv/`, `__pycache__/`, `.idea/`, `.vscode/`, `.env`, `node_modules/`.

Проверить, что файл действительно игнорируется:

```bash
git check-ignore -v .env
```

Если файл уже был закоммичен, одного `.gitignore` недостаточно:

```bash
git rm --cached .env
git commit -m "chore: убран .env из репозитория"
```

## 10. Чего не делать

- Не коммитить секреты, пароли, токены и ключи.
- Не делать `push --force` в общие ветки.
- Не переписывать (`rebase`, `commit --amend`) историю, которая уже на GitHub.
- Не хранить в репозитории `project_final_v2_real_final.zip`.
- Не делать один огромный коммит «на всё».

## 11. Если что-то пошло не так

```bash
git status                    # первое, что нужно смотреть
git restore <файл>            # отменить изменения в рабочей копии
git restore --staged <файл>   # убрать из индекса
git reset --soft HEAD~1       # отменить последний коммит, оставив изменения
git reflog                    # найти потерянный коммит
```

> `git reset --hard` удаляет незакоммиченные изменения безвозвратно —
> используйте осознанно.
