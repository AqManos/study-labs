# Чистый код: краткие принципы

Выжимка из книги Роберта Мартина «Чистый код» (Clean Code) и смежных практик.
Книга — **рекомендация**, а не догма: принципы стоит применять с головой.

Ссылка: <https://www.litres.ru/book/robert-s-martin/chistyy-kod-sozdanie-analiz-i-refaktoring-pdf-epub-70729888/>

## Имена

- Имя должно отвечать на вопрос «что это?»: `elapsedTimeInDays`, а не `d`.
- Избегайте сокращений, кроме общепринятых (`id`, `url`, `http`).
- Булевы значения — с `is`/`has`/`can`: `isActive`, `hasAccess`.
- Функции — глаголы: `calculateTotal()`, `sendEmail()`.
- Одна и та же сущность — одно и то же имя во всём проекте.

## Функции

- Маленькие: 5–20 строк, одна ответственность.
- Один уровень абстракции на функцию.
- Минимум параметров; 3+ параметра — повод задуматься об объекте.
- Без «флагов»-аргументов, которые переключают поведение.
- Без побочных эффектов, не очевидных из имени.

## Комментарии

- Хороший код говорит сам за себя; комментарий объясняет **почему**, а не «что».
- Не комментируйте очевидное.
- Устаревший комментарий хуже отсутствующего.
- TODO должен содержать причину или ссылку на задачу.

## Форматирование

- Единый стиль во всём проекте (отступы, кавычки, порядок импортов).
- Для Python — PEP 8 + `ruff`/`black`; для JS/TS — `eslint` + `prettier`.
- Файл должен читаться сверху вниз: сначала высокоуровневая логика, детали — ниже.
- Не оставляйте закомментированный код «на всякий случай» — для этого есть Git.

## Обработка ошибок

- Не игнорируйте исключения (`except: pass` — почти всегда ошибка).
- Сообщения об ошибке должны помогать диагностике: что случилось и где.
- Не возвращайте `null`/`None` в качестве сигнала об ошибке, если можно бросить
  исключение или вернуть явный результат.
- Проверяйте входные данные на границах системы.

## Классы и модули

- Single Responsibility: у класса одна причина для изменения.
- Небольшие классы; если файл больше 300–500 строк — повод присмотреться.
- Зависимости передавайте снаружи (DI), а не создавайте внутри.
- Избегайте глобального состояния.

## Тесты

- Тест — такой же код, к нему применимы те же требования.
- Один тест проверяет одну вещь.
- Имена тестов описывают сценарий: `test_withdraw_insufficient_funds_raises`.
- Тесты должны быть быстрыми и независимыми друг от друга.

## Общие принципы

- **DRY** — не дублируйте логику.
- **KISS** — выбирайте простейшее рабочее решение.
- **YAGNI** — не пишите код «на будущее», если он не нужен сейчас.
- **Boy Scout Rule** — оставляйте код чище, чем он был до вас.
- Рефакторинг — отдельными коммитами, не смешивая с новой функциональностью.

## Чек-лист перед PR

- [ ] Имена понятны без контекста.
- [ ] Нет мёртвого и закомментированного кода.
- [ ] Нет секретов и локальных путей вроде `C:\Users\...`.
- [ ] Нет отладочных `print`/`console.log`.
- [ ] Обработаны ошибки и крайние случаи.
- [ ] Обновлён README, если изменился запуск или структура.
- [ ] Изменения не содержат посторонних файлов.
